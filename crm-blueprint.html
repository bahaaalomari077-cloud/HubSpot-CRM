Building a CRM on the Bitrix24 Model

The decisive finding. All six entities share roughly 30 identical fields — assignedById, createdTime, stageId, opportunity, currencyId, the five UTM fields, and the four lastCommunication* timestamps. Bitrix24 is not six separate tables. It is one item abstraction with per-type field sets layered on top. That single observation should drive your entire schema design.

Note the double row. Bitrix24 declares money as double — a floating-point type. Do not copy this. Floating point cannot represent 0.10 exactly, and repeated addition across a pipeline drifts. Use numeric(18,2), or store integer minor units. This is one of the few places where the reference implementation is worth deliberately diverging from.

The multifield pattern

A contact has several phone numbers, each with a label (work, mobile, fax), each possibly the primary. Bitrix24 calls this crm_multifield and stores it as a child table rather than as columns. Copy this exactly — every CRM that starts with phone1, phone2, phone3 eventually regrets it.

CREATE TABLE multifield (
  id          bigserial PRIMARY KEY,
  entity_type smallint  NOT NULL,   -- 1 lead, 2 deal, 3 contact…
  entity_id   bigint    NOT NULL,
  kind        text      NOT NULL,   -- PHONE | EMAIL | IM | WEB
  value_type  text      NOT NULL,   -- WORK | MOBILE | HOME | FAX
  value       text      NOT NULL,
  is_primary  boolean   NOT NULL DEFAULT false,
  sort        int       NOT NULL DEFAULT 100
);
CREATE INDEX ON multifield (entity_type, entity_id);
CREATE INDEX ON multifield (kind, value);  -- dedupe + inbound call lookup

That second index is what makes "an unknown number is calling — who is this?" resolve in milliseconds. Inbound identification is a core CRM behavior, not an afterthought.

03Data model

The shared-core observation from section 01, turned into tables.

Why one core table, not six

Six near-identical tables means every feature — assignment, stage movement, search, permissions, audit, timeline — gets written six times and drifts. A shared core writes each once. The cost is that the core table grows wide and holds columns irrelevant to some types (probability means nothing on a Contact). That trade is worth taking, and it is the trade Bitrix24 itself made.

Two viable shapes:

  • Single table with a type discriminator. Simplest joins, simplest permissions. Nullable columns for type-specific fields. Start here.
  • Core table plus per-type extension tables. Cleaner nullability, one extra join on every read. Worth it past roughly 60 type-specific columns.
CREATE TABLE crm_item (
  id              bigserial,
  entity_type_id  smallint    NOT NULL,
  tenant_id       bigint      NOT NULL,
  title           text,
  -- pipeline position
  pipeline_id     bigint      REFERENCES pipeline,
  stage_id        bigint      REFERENCES stage,
  stage_semantic  text        NOT NULL DEFAULT 'process',
  -- money
  amount          numeric(18,2) NOT NULL DEFAULT 0,
  currency_id     char(3)     NOT NULL DEFAULT 'USD',
  amount_base     numeric(18,2),  -- converted, for cross-currency rollups
  is_manual_amount boolean    NOT NULL DEFAULT false,
  -- ownership & access
  assigned_by_id  bigint      NOT NULL REFERENCES users,
  is_open         boolean     NOT NULL DEFAULT true,
  -- audit (present on every Bitrix entity)
  created_by      bigint      NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_by      bigint,
  updated_at      timestamptz NOT NULL DEFAULT now(),
  moved_by        bigint,
  moved_at        timestamptz,
  -- denormalized for list sorting; Bitrix does exactly this
  last_activity_at   timestamptz,
  last_comm_call_at  timestamptz,
  last_comm_email_at timestamptz,
  -- attribution
  source_id       bigint      REFERENCES status_ref,
  utm             jsonb,      -- 5 UTM fields collapse to one column

  PRIMARY KEY (entity_type_id, id)
);

-- the index every kanban query needs
CREATE INDEX ON crm_item
  (tenant_id, entity_type_id, pipeline_id, stage_id)
  INCLUDE (amount, assigned_by_id)
  WHERE deleted_at IS NULL;

On the five UTM columns. Bitrix24 stores utmSource, utmMedium, utmCampaign, utmContent, utmTerm as five separate columns on every entity — 25 columns across the model that are almost always null. Collapse them into one jsonb. You keep queryability through a GIN index and lose nothing.

Custom fields

Bitrix24 lets users define their own fields at runtime, which rules out a fixed schema. Two workable approaches, and the choice matters:

Option A
jsonb column

One custom jsonb column on crm_item. GIN-indexed. No joins, trivially fast reads, flexible.

Weak per-field typing and constraints. Recommended — simpler, and Postgres jsonb is fast enough.

Option B
EAV table

field_value(item, field_def, value). Proper per-field types, constraints, referential integrity.

One join per field queried. Painful for wide list views.

Timeline and activity — keep them separate

These look alike and are not. An activity is something scheduled that someone must do — it has a due date, an owner, and a completed flag, and it drives the "overdue" counters. A timeline entry is something that already happened — immutable, append-only, the audit record. Merging them produces a table that is both a work queue and a log and is bad at both.

04Technology stack

Choices with reasons. The load pattern here is read-heavy, relational, with real-time board updates and heavy filtering.

Database
PostgreSQL 16

Relational integrity for the entity graph, plus jsonb for custom fields and UTM — you need both, and Postgres is the one engine that does both well. Row-level security maps cleanly onto CRM permissions.

Not MongoDB: a CRM is a graph of related records, and you will join constantly.

Backend
NestJS + TypeScript

The shared-core model needs strong typing to stay safe across entity types. Module structure mirrors CRM domains naturally.

Go/Rust if the team knows them — faster, but slower to build this shape.

ORM
Drizzle

SQL-first, so the deliberate index work above survives contact with the ORM. Typed results without a query-builder abstraction fighting you.

Prisma is friendlier; it obscures query plans you will need to tune.

Frontend
React + TanStack Query

The board is a cache-coherency problem, not a rendering problem. TanStack Query's optimistic updates are exactly the drag-and-drop pattern.

Svelte/Vue equally fine; the data layer choice matters more.

Drag & drop
dnd-kit

Accessible by default — keyboard and screen reader support that react-beautiful-dnd (now unmaintained) lacks.

Native HTML5 DnD for a simple board; it degrades badly on touch.

Search
Postgres FTS → Meilisearch

Start with tsvector; it carries you to ~1M records. Move to Meilisearch when typo tolerance and faceting start to matter.

Elasticsearch is heavier than this workload needs.

Realtime
Centrifugo

Bitrix24 pushes live board updates ("server connection established" in its own UI). Centrifugo handles fan-out without coupling it to your app servers.

Plain WebSockets work until you run more than one backend instance.

Jobs & automation
BullMQ + Redis

Automation rules are delayed, retryable jobs. Also covers email send, import, and rollup recalculation.

pg-boss if you want to avoid adding Redis.

The automation engine

Bitrix24's automation rules fire on stage entry. Model a rule as (trigger, condition, action) and keep execution in the queue, never inline in the HTTP request — a rule that sends email must not make the drag feel slow, and it must survive a failed send.

// stage change emits; the rule engine consumes
await tx.insert(timeline).values({ itemId, type: 'stage_changed', from, to });
await queue.add('automation', { itemId, trigger: 'stage_entered', stageId: to },
  { attempts: 3, backoff: { type: 'exponential', delay: 2000 } });

05Permissions — decide this before you build

Every entity in the schema carries assignedById, opened, and observers. Those three columns are a full access model, and retrofitting one later means rewriting every query in the system.

  • assigned_by_id — the owner. The baseline "my records" filter.
  • is_open — visible to everyone, regardless of owner. Note it is the one field Bitrix marks required on all six entities.
  • observers — extra users with read access. A join table.
  • Department hierarchy — managers see subordinates' records, transitively.

Implement as a predicate appended to every list query, ideally via Postgres row-level security so it cannot be forgotten at a call site:

CREATE POLICY item_read ON crm_item FOR SELECT USING (
  tenant_id = current_tenant()
  AND (
    is_open
    OR assigned_by_id = current_user_id()
    OR assigned_by_id = ANY(subordinate_ids(current_user_id()))
    OR EXISTS (SELECT 1 FROM observer o
                WHERE o.item_id = crm_item.id AND o.user_id = current_user_id())
  )
);

06Build sequence

Ordered so each phase is usable on its own, and so the expensive-to-change decisions land first.

  1. Foundation Must

    Tenancy, users, departments, auth. The crm_item core with Contact and Company only. Multifield table. Row-level security from the first query — not bolted on later.

    Ships: working contact database with search and permissions

  2. Deals and the board Must

    Pipelines, stages, semantics. Kanban with optimistic drag-and-drop. Stage-change events written to timeline. Per-stage rollups.

    Ships: the screen this blueprint started from

  3. Timeline and activities Must

    Append-only timeline. Scheduled activities with due dates driving overdue counters. Comments. This is where a CRM stops being a spreadsheet.

    Ships: history and follow-up

  4. Custom fields Should

    Field definitions per entity type, jsonb storage, dynamic form rendering, filter integration. Deferring past this point means migrating live data.

    Ships: tenant-specific configuration

  5. Quotes and invoices Should

    Line items, tax, totals, PDF generation, payment status. New entity types on the existing core — this phase proves the core abstraction was right.

    Ships: quote-to-cash

  6. Automation Should

    Trigger/condition/action rules on stage entry. Queue-backed. Start with three actions — assign, notify, create activity — before building a visual editor.

    Ships: the pipeline runs itself

  7. Communications Later

    Email sync, telephony, inbound number resolution via the multifield index. Each channel is a genuine integration project; do not underestimate these.

    Ships: contact center

  8. Reporting Later

    Funnel conversion, win rate, forecast, activity volume. Read replica or a rollup table — never run analytics against the live board's tables.

    Ships: management view

07What to do differently

Five places where copying Bitrix24 exactly would be a mistake.

  • Money as numeric, not double. The single clearest flaw in the reference schema.
  • UTM as one jsonb, not five columns per entity. Removes 25 mostly-null columns.
  • Decide Leads early. Bitrix24 supports both a lead-first and a lead-free flow, and that flexibility costs real complexity. If your process does not need a separate qualification stage, skip the Lead entity entirely — it is 52 fields and an entire conversion pathway.
  • Don't build the visual automation editor first. Three hardcoded rule types cover most real usage; the editor is months of work serving the last 10%.
  • Ship one pipeline before making pipelines configurable. The data model should support many from day one; the UI does not have to.

Scope reality. What is mapped here — phases 1 through 6 — is the CRM core, and it is a substantial build. The full Bitrix24 surface also includes Tasks, Booking, Inventory, Marketing, Sites, BI Builder, e-Signature, Knowledge Base, and a telephony contact center. Each is its own product. Treat this blueprint as the CRM, not as the suite.
